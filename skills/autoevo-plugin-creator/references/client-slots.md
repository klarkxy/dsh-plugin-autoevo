# Client Slot UI

First select the narrowest UI surface matching the requested user action. Then inspect that exact Slot contract and use the returned registration protocol (`single`, `list`, `keyed`, or `chain`), options, props, occupants, and replacement risk.

Use the confirmed Slot service defensively, wait for its selected declaration, and register inside that lifecycle callback. Prefer additive inner Slots over replacing an existing layout region. Do not guess a Slot name, `id`, `key`, selector, prop, or a root/sidebar target.

Use `React.createElement`, not JSX. Read only the scalar fields needed from Slot props or snapshots. Keep component interaction state transient. Choose a settings section for a full settings experience; use a compact settings item only for one compact preference.

When the UI belongs directly beside the latest Cordis run result, use the confirmed run-card Slot and its prescribed self-binding key. For an ordinary Tool card, first confirm the Tool schema and complete owner props because an existing key can replace the product card.

Verify real rendering and the requested interaction in a responding Client. A Host-only successful run is not proof of Client UI behavior.
